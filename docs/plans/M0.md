## Labels
- **`cloud`**: built in a cloud session and fully provable by committed tests.
- **`cloud+local`**: built in a cloud session, but it cannot merge without the owner's machine: the
  real-drawing check (every engine PR), a check on the real files, the design gate, or a walk on a
  real set. Each such ticket names its local step and who does it.
- **`local`**: needs real drawings or the owner's eyes throughout; built in a local session.
- **`owner`**: the owner does it; an agent may prepare it.

"Engine PR" means a diff touching `engine/**`, `vextrus/drawings/**`,
`vextrus/takeoff/services/read_propose/**`, `vextrus/takeoff/services/export.py`,
`vextrus/takeoff/tasks/**`, `tools/acadsharp-dump/**`, `toolchain/**` or `uv.lock` (a reading
library's upgrade changes reading). 01c's not-applicable job holds this list; the owner reads
`.github/` in full, so it cannot be quietly narrowed.

## The shape of M0's code
- **Backend:** one uv project. `vextrus/<module>/` for the 12 Django modules; `engine/` is a
  top-level package beside `vextrus/` (no Django, no module imports). Always import the platform
  module as `vextrus.platform` (a bare `platform` is Python's standard library).
- **Module anatomy** (ADR 0034, with packages where parallel tickets would otherwise share a file):
  `models.py` and `migrations/` (private; only the one ticket per wave that adds a migration to the
  module edits `models.py`); `services/`, `schemas/`, `http/`, `admin/`, `tasks/` as packages, each
  ticket owning its own submodule (`platform/services/jobs.py`, `platform/http/auth.py`); `tests/`.
  `services/__init__.py` and `schemas/__init__.py` re-export; a re-export line is the only shared
  edit. `http/__init__.py` exposes one `router` that includes the submodules' routers.
- **Settings** are a package, `vextrus/settings/` (`base`, `db`, `auth`, `tenancy`, `jobs`,
  `storage`, `uploads`, `jev`, `test`). 01a writes every M0 setting's name and default in its
  submodule; a ticket changes values only in the submodule it owns.
- **Engine:** `engine/read/` (`artefact.py`, `anchor.py`, `sandbox.py`, `libredwg/`, `acadsharp/`,
  `pdf/`), `engine/text/` (decoding), `engine/recognise/` (`types.py`, `sheets.py`, `register.py`,
  `storeys.py`, `views.py`, `scales.py`), `engine/render/` (`buffers.py`, `fonts/`), `engine/plot/`
  (`registration.py`), `engine/check/` (one file per Check, `catalogue.py` scanning the directory),
  `engine/harness.py`, `engine/export.py`. Tests sit beside each subpackage (`engine/read/tests/`).
  M0 has no Element Families (`engine/families/` arrives with M1).
- **Fixtures:** a synthetic DWG is never committed (the guard refuses staging `.dwg`). Each fixture
  is its own generator, `engine/fixtures/dwg/<name>.py`, run at test time into pytest's temporary
  directory and cached per session, so tickets adding fixtures never share a file.
- **Frontend:** `web/` (Vite, React 19, TypeScript, Tailwind v4 tokens). Features by folder:
  `web/src/ui/` (shared components and the key map), `web/src/app/` (the frame), `web/src/format/`,
  `web/src/auth/`, `web/src/projects/`, `web/src/drawing-set/`, `web/src/sheet/`, `web/src/takeoff/`.
  Routes are TanStack Router file routes under `web/src/routes/<feature>/`; the route tree is
  generated at build time and never committed, so no ticket edits a shared route table. The status
  bar and toolbar take contributions through slots (a feature registers an item; it never edits the
  frame's files). Generated API types are built in CI and never committed.
- **Seed:** `uv run manage.py seed_demo` loads an invented demo project (invented Developers, users,
  a project, a Drawing Set from synthetic DWGs, invented sheets, Proposals and Questions) for walking
  every UI PR. 01a writes the command and `vextrus/seed/<module>.py` stubs; each ticket fills its
  module's seed. Nothing in it comes from a real set.
- **Harness:** `scripts/score/` (vx-score; the owner installs it to `/usr/local/bin`),
  `scripts/real-drawings` and `scripts/real_drawings/` (the owner's command), `scripts/owner/`,
  `scripts/cloud/`, `.github/`. The owner reads these and `engine/read/sandbox.py` in full, beside
  `.github/`, `.claude/`, migrations and tests ("For the owner", item 3).
- **Migrations:** each module's own chain; at most one ticket per wave adds a migration to a module;
  CI asserts one leaf per module and `makemigrations --check`.
- **CI:** required checks are never filtered by path at the workflow level (a skipped workflow
  leaves a required check waiting); jobs skip by `if:` from a changes step instead, which also saves
  minutes. Concurrency cancels superseded runs per branch; uv and npm caches on.

## The contracts fixed here (so tickets in one wave can build against each other)
**Engine stages** (06b's harness calls them by these names; a stage whose function does not exist yet
is reported "not built", never faked):
`engine.read.read(path) → ReadArtefact` (04) · `engine.check.decoders_agree.run(path, artefact)` (10)
· `engine.read.pdf.report(path)` and `engine.read.pdf.page_text(path)` (12) ·
`engine.render.fonts.report(artefact)`, `engine.check.bangla_ansi.run(artefact)` (11) ·
`engine.recognise.sheets.find(artefact, file_discipline) → list[SheetCandidate]` and
`engine.recognise.register.find(artefact, sheets)` (13) ·
`engine.recognise.views.find(artefact, sheet) → list[ViewCandidate]` (17) ·
`engine.render.buffers.build(artefact, sheet)` (11) · `engine.plot.registration.match(pages, sheets)`
and `engine.check.render_f1.score(buffers, page, transform)` (18) · `engine.check.catalogue.run_all(…)`
(19b) · `engine.export.build(…)` (06b). Each Check module declares `CODE`, `VERSION`, `MILESTONE`.
**Candidate types** live in `engine/recognise/types.py` (06b): a SheetCandidate carries its location
(model-space box or layout), number, title, Discipline, revision mark, issue date, storeys as stated,
each value's source (attribute, title-block text, file) and anchors; a ViewCandidate carries box,
title, kind (the one list above), not-to-scale, stated scale, storeys (list and meaning), proposed
Takeoff Steps or exclusion reason, and anchors. A JudgementRequest names the node, facts, question
and options.

**The export** (one JSON document per Drawing Set; 06b writes it, 05 validates and scores it): run id,
commit, code hash; per file: sha256, format, Discipline default, decoders agree, read seconds, peak
RSS; sheets (as the SheetCandidate, with title decoded); views (as the ViewCandidate); register
entries; Plot matches per PDF page (sheet or the reason none matched, residual); render F1 per sheet;
Check results; Coverage per view.

**The key** (with the key user only; 06c and 06d write it): per Development Set, the join rule;
per sheet: number, title, Discipline, storeys list, revision mark, and for the Sample Project its
frame box or layout; per view (level 2): its sheet, its reading-order position, kind, not-to-scale,
storeys list and meaning; the register's N and the PDF page count.

**Matching** (fixed now, never tuned after a result): the Sample Project joins a sheet by frame
IoU ≥ 0.9 or a shared layout, a view by IoU ≥ 0.8 with the same kind. **Edison joins by identity:**
a sheet by its normalised sheet number (case, whitespace, and `-`/`.`/space separators folded), then
by normalised title for sheets with no number; a view inside a matched sheet by reading order (rows
top to bottom, left to right, after the key's page rotation is undone) and kind. A title matches when
equal after normalising case, whitespace and decoded symbols; storeys when the lists are equal.
Export sheets and views that join nothing are phantoms.

## The real-drawing check (06a builds it; ADRs 0026 and 0030 as amended)
1. The owner runs `scripts/real-drawings <PR number | main>` in a WSL terminal.
2. It checks out the PR's head into a scratch worktree under the owner's cache and runs
   `uv sync --frozen --no-build` (wheels only, so no package build script runs).
3. It runs the pipeline **as the owner, inside bwrap:** no network; environment cleared; bound
   read-only: `/usr`, the toolchain, the scratch checkout and the two Development Sets; writable: one
   scratch directory and the drop folder `/srv/vextrus-drop`. Not mounted: the owner's home (its
   secrets, `gh` token and the laboratory) and the key user's home. Until 21c it runs the engine
   harness (06b); from 21c the product's read-and-propose job against a throwaway Postgres cluster
   started inside the sandbox on a Unix socket. With no network, Jev is unavailable, so the check
   measures code alone; the Jev node is measured by ticket 23.
4. It writes the export and the run's metadata (run id, commit, code hash) to the drop folder, clearing
   it first.
5. It runs the scorer as the key user; `sudo` asks the owner's password. vx-score takes no path: it
   reads only the drop folder and the keys, checks the export's run id, prints aggregates per measure
   (n / N, phantoms, the change from the last merged run) and posts the `real-drawings` status.
6. Per-step results are cached by (input file sha256, step, code hash): the code hash covers
   `engine/`, the reading modules, `toolchain/` and `uv.lock`. A rebase onto a non-engine merge
   reuses the cache; an engine merge reruns the changed steps only.

**What it reports before 13 merges:** decoder agreement per file (from 10), each file's entity counts
per type against the last merged run (a change is shown), read time and peak memory per file, the font
and PDF reports' counts, and the sheet and view measures as 0 / N (no segmentation yet). From 13:
sheets, numbers, titles, Discipline, register. From 17: views, not-to-scale, storeys, Coverage. From
18: Plot pages matched and render F1.

**The `real-drawings` requirement** enters the ruleset only after 06e's first run on `main` succeeds;
that run is the baseline for everything merged before it. Engine PRs merged earlier (04, perhaps 06b,
10, 11, 12) say "not measured on real drawings" in their body, and 06e measures them on `main`.

### For the owner (new decisions this plan needs)
1. **The identity the `real-drawings` status is posted with.** Recommendation: a small private GitHub
   App you own, with only "commit statuses: write" on this repository, its key kept in the key user's
   home; vx-score posts as it. Why: agents use your `gh` token, so a status posted with it cannot be
   told from a forged one; with the App, the PR shows the check's author, and you merge only on that
   author. (Pinning the ruleset to the App would also block CI's "not applicable", so it stays
   unpinned.)
2. **A read-only token for the LibreDWG release asset in the cloud environments,** only if the
   first-session checklist shows `gh` cannot download it through the proxy. Recommendation: yes, a
   fine-grained token with read access to this repository only, as an environment credential. Why:
   the fallback builds LibreDWG from source inside the setup's five-minute budget, which it may not
   meet; sessions can already read the repository, so the token widens nothing.
3. **You read the harness scripts and the sandbox in full** (`scripts/real-drawings`,
   `scripts/real_drawings/`, `scripts/score/`, `scripts/owner/`, `scripts/cloud/`,
   `engine/read/sandbox.py`), beside ADR 0025's list. Recommendation: yes. Why: they decide what the
   PR's code can reach while your keys are one password away.
4. **Who converts the Sample Project's generating inputs into its key (06c).** Recommendation: you, or
   a throwaway session you start outside the repository that takes no reading ticket in M0, as for
   the Edison drafting script. Why: whoever sees the inputs knows the answer.
