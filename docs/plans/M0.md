## The shape of M0's code
- **Backend:** one uv project on Python 3.14. `vextrus/<module>/` for the 12 Django modules
  (`platform`, `projects`, `drawings`, `live_model`, `takeoff`, `measurement`, `rates`, `boq`,
  `revisions`, `summary`, `exports`, `assistant`); `engine/` is a top-level package beside `vextrus/`
  (no Django, no module imports). Always import the platform module as `vextrus.platform` (a bare
  `platform` is Python's standard library).
- **Module anatomy** (ADR 0034, with packages where parallel tickets would otherwise share a file):
  `models.py` and `migrations/` (private; only the one ticket per wave that adds a migration to the
  module edits `models.py`); `services/`, `schemas/`, `http/`, `admin/`, `tasks/` as packages, each
  ticket owning its own submodule (`platform/services/jobs.py`, `platform/http/auth.py`); `tests/`.
  `services/__init__.py` and `schemas/__init__.py` re-export; a re-export line is the only shared
  edit. `http/__init__.py` exposes one `router` that includes the submodules' routers.
- **Ids:** every row's id comes from `vextrus.platform.ids.new_id()` (a UUIDv7 over Python 3.14's
  `uuid.uuid7`), made in the app, with no database default; no migration names `uuid.uuid7`.
- **Settings** are a package, `vextrus/settings/` (`base`, `db`, `auth`, `tenancy`, `jobs`,
  `storage`, `uploads`, `jev`, `i18n`, `test`). 01a writes every M0 setting's name and default in its
  submodule; a ticket changes values only in the submodule it owns.
- **Messages:** every sentence the machine writes (a Question, a Check finding, a file report, an
  exclusion reason, a status word, an act in the event log) is stored and sent as a message code and
  named parameters, never as prose. Each module declares its codes as an enum in
  `vextrus/<module>/schemas/messages.py`, which the OpenAPI schema carries; the web words each code from
  its feature's catalogue. Text a person types and drawing text are data, kept as entered.
- **Engine:** `engine/read/` (`artefact.py`, `anchor.py`, `sandbox.py`, `libredwg/`, `acadsharp/`,
  `pdf/`), `engine/text/` (`decode.py`, `mtext.py`), `engine/geometry/` (`placement.py`),
  `engine/recognise/` (`types.py`, `sheets.py`, `register.py`, `storeys.py`, `views.py`, `scales.py`,
  `conflicts.py`), `engine/render/` (`buffers.py`, `fonts/`), `engine/plot/` (`registration.py`),
  `engine/check/` (one file per Check, `catalogue.py` scanning the directory), `engine/harness.py`,
  `engine/export.py` and `engine/export.schema.json`. Tests sit beside each subpackage
  (`engine/read/tests/`). M0 has no Element Families (`engine/families/` arrives with M1).
- **Fixtures:** a synthetic DWG is never committed (the guard refuses staging `.dwg`). Each fixture
  is its own generator, `engine/fixtures/dwg/<name>.py` (PDFs: `engine/fixtures/pdf/<name>.py`), run at
  test time into pytest's temporary directory and cached per session, so tickets adding fixtures never
  share a file.
- **Frontend:** `web/` (Vite, React 19, TypeScript, Tailwind v4 tokens, Lingui). Features by folder:
  `web/src/ui/` (shared components, `LtrCanvas`, `DrawingText` and the key map), `web/src/app/` (the
  frame), `web/src/format/`, `web/src/auth/`, `web/src/projects/`, `web/src/members/`,
  `web/src/drawing-set/`, `web/src/sheet/`, `web/src/takeoff/`. **Each feature folder keeps its own
  English catalogue** (`locales/en.po`), so no ticket edits another's. Routes are TanStack Router file
  routes under `web/src/routes/<feature>/`; the route tree is generated at build time and never
  committed, so no ticket edits a shared route table. The status bar and toolbar take contributions
  through slots (a feature registers an item; it never edits the frame's files). CSS is logical only,
  and the sheet canvas sits inside `LtrCanvas`, fixed left to right. Generated API types are built in
  CI and never committed.
- **Seed:** `uv run manage.py seed_demo` loads the invented demo project of docs/design/m0-screens.md §7
  for walking every UI PR: both Developers on the Bangladesh Market, each project with its Site and one
  Building, the outside member given one project with an end date. 01a writes the command and
  `vextrus/seed/<module>.py` stubs; each ticket fills its module's seed; 03 ships a static copy for
  shell work before the API exists; from 21c the seed's synthetic files go through the real read job.
  Nothing in it comes from a real set. (m0-screens §9's ruling 5, "the seed is written by ticket 20,
  extended by 21", predates this plan's split of 20; the per-module seed was signed with the plan.)
- **Harness:** `scripts/real-drawings` and `scripts/real_drawings/` (the owner's command),
  `scripts/owner/`, `scripts/cloud/`, `.github/`; `scripts/score/` (vx-score) arrives with M1. The owner
  reads these and `engine/read/sandbox.py` in full, beside `.claude/`, migrations and tests ("For the
  owner", item 3).
- **Lints in CI:** ruff, mypy, import-linter, the migration scan, the market-literal scan
  (`tools/lint/`), and on the web the catalogue lint and the logical-CSS lint.
- **Migrations:** each module's own chain; at most one ticket per wave adds a migration to a module;
  CI asserts one leaf per module and `makemigrations --check`. Every table is created with its
  in-module references in its first migration: under forced RLS a key added to a populated table fails
  (docs/data-model.md §2).
- **CI:** Python 3.14 (setup-python), a `postgres:18.6` service, g++ for ezdxf. Required checks are
  never filtered by path at the workflow level (a skipped workflow leaves a required check waiting);
  jobs skip by `if:` from a changes step instead, which also saves minutes. Concurrency cancels
  superseded runs per branch; uv and npm caches on.

## The contracts fixed here (so tickets in one wave can build against each other)
**Engine stages** (06b's harness calls them by these names; a stage whose function does not exist yet
is reported "not built", never faked):
`engine.read.read(path) → ReadArtefact` (04) · `engine.check.decoders_agree.run(path, artefact)` (10)
· `engine.read.pdf.report(path)` and `engine.read.pdf.page_text(path)` (12) ·
`engine.render.fonts.report(artefact)`, `engine.check.bangla_ansi.run(artefact)` (11) ·
`engine.recognise.sheets.find(artefact, file_discipline) → list[SheetCandidate]` and
`engine.recognise.register.find(artefact, sheets)` (13) ·
`engine.recognise.views.find(artefact, sheet) → list[ViewCandidate]` (17) ·
`engine.render.buffers.build(artefact, sheet)` (11) · `engine.plot.registration.match(pages, sheets)`
and `engine.check.render_f1.score(buffers, page, transform)` (18) ·
`engine.recognise.conflicts.find(sheets, views)` and `engine.check.catalogue.run_all(…)` (19b) ·
`engine.export.build(…)` (06b). Each Check module declares `CODE`, `VERSION`, `MILESTONE`.

**Placement** (s02, the Edison check's generic bugs; 04 supplies the raw values, 11 resolves them): the
ReadArtefact carries each insert's insertion point, scale, rotation and extrusion, and each MTEXT's
height as stored (possibly none) and its direction vector, unresolved.
`engine.geometry.placement.world(entity, chain)` returns the object-to-world transform through the
whole insert chain, a mirrored insert (extrusion −Z) included; `engine.text.mtext.height(entity, chain)`
never returns none (its own, else its style's, else its block's; a finding when all are missing);
`engine.text.mtext.angle(entity)` reads the direction vector. The renderer (11) and the recognisers (13,
17) never compute either themselves.

**Candidate types** live in `engine/recognise/types.py` (06b): a SheetCandidate carries its location
(model-space box or layout), number, title, Discipline (one of six: `structural`, `architectural`,
`electrical`, `plumbing` (plumbing and sanitary), `fire`, `other_mep`), revision mark, issue date,
storeys as stated, each value's source (a title-block attribute, text by its place in the title block,
the file) and anchors; a ViewCandidate carries box, title, kind (the one list: plan, section,
elevation, schedule, detail, notes, legend, title block, key plan, 3D/perspective), not-to-scale,
stated scale, storeys (an explicit list and what it means), and its proposed Takeoff Steps, or its
Discipline Part for an MEP view, or its exclusion reason, and anchors; a Conflict names its kind, the
candidates and the evidence; a JudgementRequest names the node, facts, question and options. The engine
knows no Building: `drawings` assigns each sheet to the Project's Building.

**The export** (one JSON document per Drawing Set; 06b writes it and its JSON Schema; the real-drawing
check diffs it; M1's scorer extends it): run id, commit, code hash; per file: sha256, format, Discipline
default, decoders agree, entity counts per type, read seconds, peak RSS, the font and PDF reports'
counts, the Bangla-ANSI count; sheets (as the SheetCandidate, title decoded); views (as the
ViewCandidate); register entries; conflicts; Plot matches per PDF page (the sheet, or the reason none
matched, and the residual); render F1 per sheet; Check results; Coverage per view. It holds drawing
text, so it never leaves the owner's machine.

**Run-to-run matching** (06a; fixed now, never tuned after a result). Both runs read the same files, so
items join by where they are, not by what they say: a sheet by (file sha256, layout name) or (file
sha256, model-space frame box with IoU ≥ 0.9); a view inside a joined sheet by IoU ≥ 0.8; a Plot match
by (PDF sha256, page); entity counts by (file sha256, type); render F1 by the joined sheet. An item that
joins nothing in the other run is **gained** or **lost**. A joined item whose value differs (number;
title after normalising case, whitespace and decoded symbols; Discipline; revision mark; storeys list
and meaning; kind; not-to-scale; stated scale; Coverage status; the page's sheet; decoders agree) is
**changed**. A sheet's render F1 is changed when it moves by more than 0.005 and lost when it falls by
more than 0.01. Read time and peak memory are shown, never counted. **The key and its matching** (the
signed plan's Edison identity join and the Sample Project's IoU) move to M1 with vx-score, unchanged
(M1 ticket 01).

**Message codes** (each ticket for its module): a machine sentence is `{code, params}`; the codes are an
enum per module, carried by the OpenAPI schema into the generated types; the web words each code from
its feature's catalogue; 03's test fails when a code in the generated types has no English message.

**The Market on the web** (07 sends it; 03 formats with it): `/api/me` carries the current Developer's
Market: language and direction, format profile (grouping, digits, the locale each language borrows:
`en-IN` for Bangladesh's English), currency and minor units, time zone, and the unit systems offered
with the default. 03's formatters take the profile as an argument; until 20a wires `/api/me`, the shell
uses a static Bangladesh profile from the seed's static copy.

**Project scope** (02, 07, 08): `platform.services.tenancy.current_membership()` gives the role, the
end date and the Projects (none = all); `platform.services.auth.require(act, project_id)` refuses an
act the role lacks, and answers "not found" for a Project outside the scope, so its existence does not
leak; `projects.services.list` and `get` filter by the scope; every project-scoped endpoint calls
`require`.

**Coverage** (19a; this settles docs/data-model.md §3.4's open point as m0-screens 6.19 item 8 has it):
a Coverage row's status is written at read from the view's proposal (`assigned` with its CoverageStep
rows, or with its `part_key` for an MEP view whose Part's steps open in M3; `excluded` with a reason
code; `unaccounted` with neither), and the confirm service sets `confirmed_by`. Step 1 counts
"proposed" as rows not yet confirmed that are assigned or excluded, "assigned" and "excluded" as
confirmed rows, and "unaccounted" as rows with neither; "used" stays 0 in M0. **A drawing list read
from a sheet and one pasted by the QS that disagree** raise a `conflict` Question; until it is
answered, N shows "—" (19a stores both lists; 21c raises the Question).

## The real-drawing check (06a builds it; ADRs 0026 and 0030 as amended in session 02)
1. `scripts/real-drawings <PR number | branch | main> [--no-post]` runs from the owner's checkout of
   `main`, never from the PR's copy of the command. The owner runs the posting run of each engine PR;
   a local session may run `--no-post` on its own branch while it tunes (no password, no status).
2. It checks out the head into a scratch worktree under the owner's cache and installs the locked
   packages from wheels only (`uv sync --frozen --no-build`), so no package's build script runs. **One
   exception (s02):** ezdxf, which has no cp314 wheel, is built from its hash-pinned source inside the
   same sandbox as step 3 (no network, neither home), or taken from the cache where `main`'s lock built
   it. A PR whose `uv.lock` builds any other package from source is refused.
3. It runs the pipeline **as the owner, inside bwrap:** no network; environment cleared; bound
   read-only: `/usr`, the toolchain, the scratch checkout and the two Development Sets; writable: one
   scratch directory and the drop folder `/srv/vextrus-drop`. Not mounted: the owner's home (its
   secrets, `gh` token and the laboratory) and the key user's home. Until 21c it runs the engine
   harness (06b); from 21c, the product's read-and-propose job against a throwaway PostgreSQL 18
   cluster started inside the sandbox on a Unix socket. With no network, Jev is unavailable, so the
   check measures code alone; the Jev node is measured by 23.
4. It writes the export and the run's metadata (run id, commit, code hash, read time and peak memory
   per file) to the drop folder, clearing it first, and keeps a copy under the owner's cache.
5. It diffs the export, with `main`'s copy of the diff, against the last merged run's (the run of
   `main`'s current code hash, run first when not cached; a PR merged up to date has already produced
   it), under the run-to-run matching above. It prints, per measure, the counts gained, lost and
   changed; the item-level list, which holds drawing text, is written only under the owner's cache.
6. **Posting run only:** the owner reads the counts (and the item list where needed) and accepts or
   rejects the changes: the status is `success` when the owner accepts, `failure` otherwise, and a lost
   item or a lost render F1 is accepted only with a reason, which the status carries. Without keys, only
   the owner can tell a lost phantom from a lost sheet. The post runs as the key user, whose home holds
   the GitHub App's key, with the owner's password, and carries the counts, the verdict and the reason
   only. In M0 nothing reads an Answer Key.
7. Per-step results are cached by (input file sha256, step, code hash): the code hash covers
   `engine/`, the reading modules, `toolchain/` and `uv.lock`. A rebase onto a non-engine merge reuses
   the cache; an engine merge reruns the changed steps only.

**What it reports before 13 merges:** decoder agreement per file (from 10), each file's entity counts
per type, read time and peak memory per file, and the font and PDF reports' counts; sheets and views
are "not built". From 13: sheets, numbers, titles, Disciplines, revision marks, storeys as stated, the
