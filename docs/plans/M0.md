## The shape of M0's code
- **Backend:** one uv project on Python 3.14. `vextrus/<module>/` for the 12 Django modules
  (`platform`, `projects`, `drawings`, `live_model`, `takeoff`, `measurement`, `rates`, `boq`,
  `revisions`, `summary`, `exports`, `assistant`); `engine/` is a top-level package beside `vextrus/`
  (no Django, no module imports). Always import the platform module as `vextrus.platform` (a bare
  `platform` is Python's standard library).
- **Module anatomy** (ADR 0034, with packages where parallel tickets would otherwise share a file):
  `models.py` and `migrations/` (private; only the one ticket per wave that adds a migration to the
  module edits `models.py`); `services/`, `schemas/`, `http/`, `admin/`, `tasks/` and `messages/` as
  packages, each ticket owning its own submodule (`platform/services/jobs.py`, `platform/http/auth.py`,
  `platform/messages/jobs.py`); `library.py` (the module's Library rows for `sync_library`); `tests/`.
  `services/__init__.py` and `schemas/__init__.py` re-export; a re-export line is the only shared
  edit. `http/__init__.py` exposes one `router` that includes the submodules' routers.
- **Ids:** every row's id comes from `vextrus.platform.ids.new_id()` (a UUIDv7 over Python 3.14's
  `uuid.uuid7`), made in the app, with no database default; no migration names `uuid.uuid7`.
- **Settings** are a package, `vextrus/settings/` (`base`, `db`, `auth`, `tenancy`, `jobs`,
  `storage`, `uploads`, `jev`, `i18n`, `test`). 01a writes every M0 setting's name and default in its
  submodule; a ticket changes values only in the submodule it owns. `db` holds two aliases: `default`,
  connecting as `vextrus_app`, and `owner`, connecting as `vextrus`, used only by migrations,
  `sync_library` and the test flush (the reviews A1, A2).
- **Messages** (the reviews A5, R7): every sentence the machine writes (a Question, a Check finding, a
  file report, an exclusion reason, a status word, an act in the event log) is stored and sent as a
  message code and named parameters, never as prose. The codes live in a package per module,
  `vextrus/<module>/messages/`, one submodule per ticket, and in `engine/messages/`, one file per Check
  or reader (`engine/messages/decoders_agree.py`); each package's `__init__` collects its submodules by
  a glob, so no ticket edits a shared list. `vextrus/api.py` assembles every module's codes and
  `engine`'s, the DomainEvent acts among them, into the OpenAPI schema's enums, so platform's activity
  API never imports `takeoff` and `engine`'s codes reach the generated types (story 92). **Each backend
  ticket words its own codes in the same PR**, in `web/src/messages/<module>/<submodule>/en.po` (01b
  creates a folder per module and one for `engine`; one catalogue per submodule, so two tickets of one
  module in one wave never share a file); the feature folders' catalogues keep only the UI's chrome.
  Text a person types and drawing text are data, kept as entered.
- **Engine:** `engine/read/` (`artefact.py`, `anchor.py`, `sandbox.py`, `libredwg/`, `acadsharp/`,
  `pdf/`), `engine/text/` (`decode.py`, `mtext.py`), `engine/geometry/` (`placement.py`),
  `engine/recognise/` (`types.py`, `sheets.py`, `register.py`, `storeys.py`, `views.py`, `scales.py`,
  `conflicts.py`, `conventions/`), `engine/render/` (`buffers.py`, `raster.py`, `fonts/`),
  `engine/plot/` (`registration.py`), `engine/check/` (one file per Check, `catalogue.py` scanning the
  directory), `engine/messages/`, `engine/harness.py`, `engine/export.py` and
  `engine/export.schema.json`. Tests sit beside each subpackage (`engine/read/tests/`). M0 has no
  Element Families (`engine/families/` arrives with M1).
- **Fixtures:** a synthetic DWG is never committed (the guard refuses staging `.dwg`). Each fixture
  is its own generator, `engine/fixtures/dwg/<name>.py` (PDFs: `engine/fixtures/pdf/<name>.py`), run at
  test time into pytest's temporary directory and cached per session, so tickets adding fixtures never
  share a file.
- **Frontend:** `web/` (Vite, React 19, TypeScript, Tailwind v4 tokens, Lingui). Features by folder:
  `web/src/ui/` (shared components, `LtrCanvas`, `DrawingText` and the key map), `web/src/app/` (the
  frame), `web/src/format/`, `web/src/auth/`, `web/src/projects/`, `web/src/members/`,
  `web/src/drawing-set/`, `web/src/sheet/`, `web/src/takeoff/`, and `web/src/messages/` (the machine's
  codes, above). **Each feature folder keeps its own English catalogue** (`locales/en.po`) for its
  chrome, so no ticket edits another's. Routes are TanStack Router file routes under
  `web/src/routes/_app/<feature>/`, inside the frame (`web/src/routes/_app/route.tsx`), a Project's
  screens under the Project's frame, `web/src/routes/_app/p/$code/<feature>/`; a page outside the frame
  sits in a route group, such as `web/src/routes/(auth)/`, which adds no path segment, and a
  development-only page under `web/src/routes/dev/`, which a production build leaves out. The route
  tree is generated at build time and never committed, so no ticket edits a shared route table.
  The status bar and toolbar take contributions through slots (a feature registers an item; it never
  edits the frame's files). CSS is logical only, and the sheet
  canvas sits inside `LtrCanvas`, fixed left to right. Generated API types are built in CI and never
  committed.
- **Seed:** `uv run manage.py seed_demo` loads the invented demo project of docs/design/m0-screens.md §7
  for walking every UI PR (it runs `sync_library` first, or refuses, naming it): every Developer on the
  Bangladesh Market, each project with its Site and one
  Building, named "Building 1" (a name the design gate greps for, since it must never show; the review
  U9), and the outside member, now a Guest (a contractor's QS given only KR-01, with an end date; U4).
  01a writes the command and `vextrus/seed/<module>.py` stubs; each ticket fills its module's seed; 03
  ships a static copy for shell work before the API exists. **14 and
  19a seed KR-01 as rows at §7's state** (its files, sheets, views and render buffers made by 11's
  synthetic generators; its Proposals, the five Questions and Coverage), so Step 1 and the viewer are
  built and gated on it from wave 4 (U2); 21c replaces those rows with the real read job over the seed's
  synthetic files and asserts the same counts. **Every m0-screens 4.5 row state is on the seed**:
  across BP-02 and MG-01, 14 seeds those a file's own columns hold with no job (Read by one reader only
  among them), 21a those a read job carries once its job exists (a named shared edit to 19a's
  `vextrus/seed/takeoff.py`, merged after 19a), and 19a "Held, answered". **#75 seeds
  the access states 20a's screens need**: a person with current Memberships in two Developers, a

  Nothing in it comes from a real set. (m0-screens §9's
  ruling 5, "the seed is written by ticket 20, extended by 21", predates this plan's split of 20; the
  per-module seed was signed with the plan.)
- **Harness:** `scripts/real-drawings` and `scripts/real_drawings/` (the owner's command),
  `scripts/owner/`, `scripts/cloud/`, `.github/` (with `.github/engine-paths.txt`) and
  `.claude/hooks/`; `scripts/score/` (vx-score) arrives with M1. The owner reads these and
  `engine/read/sandbox.py` in full, beside `.claude/`, migrations and tests ("For the owner", item 3).
- **Lints in CI:** ruff, mypy, import-linter, the migration scan, the market-literal scan
  (`tools/lint/`), the workflow check and the guard's test (01c); on the web the catalogue lint, the
  logical-CSS lint (inline styles, `translateX` and `scrollLeft` included) and the design-docs lint
  (01b).
- **Migrations:** each module's own chain; at most one migration per module per wave, unless a
  declared merge edge orders them (wave 3 has two in `platform`: #75's `0007_…`, then 15's,
  renumbered after #75 merges); CI asserts one leaf per module and `makemigrations --check`.
  Migrations run as `vextrus`, the tables'
  owner, never as the app's role. Row-level security is enabled, not forced, so the owner's constraint
  checks see every row and a key added to a populated table validates correctly (measured, the review
  A2; docs/data-model.md §2).
- **CI:** Python 3.14 (setup-python), a `postgres:18.6` service, pytest as `vextrus_app` with
  migrations and flushes through the owner alias, ezdxf from its pinned wheel (no compiler). Required
  checks are never filtered by path at the workflow level (a skipped workflow leaves a required check

**Run-to-run matching** (06a; fixed now, never tuned after a result; widened by the review R2). Both
runs read the same files, so items join by where they are, not by what they say: a sheet by (file
sha256, layout name) or (file sha256, model-space frame box with IoU ≥ 0.9); a view inside a joined
sheet by IoU ≥ 0.8; a register entry inside a joined sheet by its row box with IoU ≥ 0.8; a Plot match
by (PDF sha256, page); entity counts by (file sha256, type); the font and PDF reports' counts by (file
sha256, the count's name); a Check result by (Check code, its joined subject); a conflict or
continuation by (kind, its joined candidates); render F1 by the joined sheet. An item that joins nothing
in the other run is **gained** or **lost**. A joined item whose value differs is **changed**: a sheet's
number, title (after normalising case, whitespace and decoded symbols), Discipline, revision mark and
its source, issue date, storeys list and meaning; a view's kind, not-to-scale, stated scale, storeys,
subject and layer, proposed Takeoff Steps, Discipline Part, exclusion reason and Coverage status; a
register entry's number, title and revision mark; a page's sheet; decoders agree; a count's value; a
Check result's outcome and its finding's code and parameters; a conflict's evidence. A sheet's render
F1 is changed when it moves by more than 0.005 and lost when it falls by more than 0.01. The move is
taken to nine decimal places, so a move exactly on an edge is on it, not past it (in floating point
0.505 − 0.5 is 0.0050000000000000044); the edges themselves do not move. Read time and peak memory are
shown, never counted. **One measure was added after the first result** (#64, 28 Sep 2026; open to the
owner's reversal): **failed stages**, joined by (file sha256, stage) or (the set, stage). A stage that
fails where it did not is lost, the reverse gained, and failing with another error kind changed; the
kind is the exception's class name or a fixed word, never the message. A file's process that did not
end `ok` (or whose export does not say) counts as its stage "process", kind its status: a process
killed before its first stage, or between two, leaves its stages skipped, none failed (the owner's
ruling, 28 Sep 2026: "Count it"). The reason for the measure: the owner's first baseline read nothing
(04's reader could not start inside the sandbox), and every measure showed 0 items, which looked clean.
A check that cannot show failure hides breakage. It adds a measure; it moves no threshold and changes
no join. **The key and its matching** (the signed plan's Edison identity
join, by normalised sheet number, then title, and views by reading order after undoing page rotation;
the Sample Project's IoU) move to M1 with vx-score, unchanged, copied word for word into M1 ticket 01

## The real-drawing check (06a builds it; ADRs 0026 and 0030 as amended in session 02)
Hardened by the session-02 reviews (R1–R4, R6, A3, A4): the install inside the sandbox, the run's own
drop folder, the poster's commit check, the widened matching and the pin check.
1. `scripts/real-drawings <PR number | branch | main> [--no-post] [--fresh] [--job]` runs from the
   owner's checkout of `main`, never from the PR's copy of the command. The owner runs the posting
   run of each engine PR; a local session may run `--no-post` on its own branch while it tunes (no
   password, no status). It refuses to run when the installed `dwgread` (under
   `/opt/vextrus/libredwg`) differs from the head's `toolchain/libredwg.version`.
2. It checks out the head into a scratch worktree under the owner's cache and refuses a head whose
   `uv.lock` holds any source but the package registry, or whose `[tool.uv]` table differs from
   `main`'s. `main`'s code then turns the head's lock into a requirements file with every hash (`uv
   export --frozen`), with ezdxf's hashes swapped for the compiled wheel's that `toolchain/ezdxf.lock`
   pins (unless it names the registry's pure wheel), and fetches every wheel into a wheel folder, binary
   only and checked by hash (the compiled one from the release the lock names). **The install runs
   inside the sandbox of step 3, offline, from that folder only**: a new environment from the
   toolchain's Python, then `pip install --no-index --find-links <the wheel folder> --only-binary :all:
   --no-deps --require-hashes -r <the requirements>`. No package's build script runs, and nothing is
   built.
3. It runs the install and the pipeline **as the owner, inside bwrap:** no network; environment
   cleared; bound read-only: `/usr`, `/opt/vextrus` (the toolchain), the scratch checkout, the wheel
   folder and the two Development Sets; **writable: one fresh scratch folder (`/work/out`) and a
   private, in-memory `/tmp`, and nothing else** (the root is remounted read-only). 04's reader starts
   its own bwrap, which cannot start without a `/tmp` (#64); the host's `/tmp` is never seen. Not
   mounted: the owner's home (its secrets, `gh` token and the laboratory), the key user's home and the
   drop folder.
   Until 21c it runs the engine harness (06b); from 21c, the product's read-and-propose job (the `--job`
   mode 21a adds to `main`'s command) against a throwaway PostgreSQL 18 cluster started inside the
   sandbox on a Unix socket. With no network, Jev is unavailable, so the check measures code alone; the
   Jev node is measured by 23.
4. Outside the sandbox, the command validates the export against `main`'s JSON Schema (and, for a PR
   that changes the schema, against its own, whose diff the owner reads), writes the run's metadata
   itself (run id, commit, code hash, the export's sha256, the run's length), and copies the export,
   taking regular files only and never following a link: a `--no-post` run into the session's scratch;
   a posting run into its own folder, `/srv/vextrus-drop/<run-id>/`, one posting run at a time under a
   lock. A copy stays under the owner's cache.
5. It diffs the export, with `main`'s copy of the diff, against the last merged run's (the run of
   `main`'s current code hash, run first when not cached or when its cached run had a failure; a PR
   merged up to date has already produced it), under the run-to-run matching above. It first names
   the stages that failed on each run, by stage, file count and error kind, never the message (a
   file's process that timed out or failed among them); then it prints, per measure, the counts
   gained, lost and changed; the item-level list, which holds drawing text, is written only under the
   owner's cache.
6. **Posting run only:** the owner reads the counts (and the item list where needed) and accepts or
   rejects the changes: the status is `success` when the owner accepts, `failure` otherwise, and a lost
   item or a lost render F1 is accepted only with a reason, which the status carries. Without keys, only
   the owner can tell a lost phantom from a lost sheet. The post runs as the key user, whose home holds
   the GitHub App's key, with the owner's password: the poster takes the run id, reads only that run's
   summary and metadata, **posts only when the run's commit equals the PR's head** at the time of
   posting, and carries the counts, the verdict and the reason only. In M0 nothing reads an Answer Key.
7. Each Development Set's export is cached by (code hash, the sandbox's version, the set's content).
   **The code hash covers every engine path** (Labels): until 21c `engine/`, `tools/acadsharp-dump/`,
   `toolchain/`, `uv.lock`, `pyproject.toml` and `.python-version`, which is what the harness executes;
   from 21c the product job's paths too. **The sandbox's version** hashes the files of `main`'s check
   that shape what runs inside the sandbox: `command.py` (the job it builds), `sandbox.py` (bwrap and
   the script), `source.py` (the checkout's files and modes) and `wheels.py` (the wheels, the compiled
   or the pure ezdxf). Any edit to one of them, a comment too, reads both sets again. **An export with
   a failed stage, or a file whose process timed out, failed or does not say, is never reused** (a
   process killed before its first stage leaves its stages skipped, none failed), **and a reused
   export is checked against the schema again**: the cache is shared with every local copy of the
   command, and a branch's copy with a looser `schema.py` could leave an entry under `main`'s key, so
   the copy that reuses checks what it reads (which is why `schema.py` is not in the sandbox's
   version). A failed or refused entry is read again. The failure may be the machine's (a
   timeout, an OOM kill, `SandboxUnavailable`), not the code's; reused, it would stand as `main`'s run,
   and as a non-engine PR's own with nothing lost, until the code hash changed. A failure the code
   causes simply repeats, at one run's cost (about 40 s on the Development Sets). `--fresh` reads the
   head and `main` again whatever the cache holds, for a change the key does not see (the host's bwrap,
   a toolchain rebuilt at the same pin). A rebase onto a non-engine merge reuses the cache; an engine
   merge reads both sets again.

**What it reports before 13 merges:** decoder agreement per file (from 10), each file's entity counts
per type, read time and peak memory per file, and the font and PDF reports' counts; sheets and views
are "not built". From 13: sheets, numbers, titles, Disciplines, revision marks and their sources, issue
dates, storeys as stated, the register. From 17: views, kinds, not-to-scale, stated scales, storey
lists, subjects and layers, proposed steps, Parts and exclusion reasons, Coverage. From 18: Plot pages
matched and render F1 per sheet. From 19b: Check results, conflicts and continuations. **From 21c:** the
product job's results; 21c's own posting run is the first in `--job` mode, diffed against the last
harness run, and the owner accepts that first harness-to-job diff item by item (the review R2).

**The baseline.** Once 04, 06a and 06b are merged, the owner runs `scripts/owner/drop-setup.sh`
(creating `/srv/vextrus-drop` and its lock; the review R6), then `scripts/real-drawings main`: the first
run, which everything later is diffed against, with its length recorded. Then `real-drawings` and
`design-gate` join the ruleset. Engine PRs merged before it (04, 06b) say "not measured on real
drawings" in their body, and the baseline measures them; UI PRs merged before it (01b, and 03 if it
merges first) carry the design gate's items passed and failed in their body. (The signed plan's 06e was
the first *scored* run; it is M1's.)
