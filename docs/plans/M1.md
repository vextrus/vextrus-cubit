## Reused from M0: the loop, unchanged
Every ticket runs M0's loop ("Finishing M0", item 3; ADR 0041; `orchestrate-wave`):
1. `acceptance-writer` commits failing tests (`acceptance:` commits, 20 minutes) before the builder starts. It runs them against a throwaway implementation, and the orchestrator rules its "not pinned" list first.
2. The builder works to its budget.
3. One `pr-reviewer` review, with `ux-critic` beside it: the walk for UI tickets, the words-only gate for backend tickets that word codes.
4. At most two fix rounds. A later finding is filed, unless it is a security hole scoring 75 or more, or a crash or false statement a QS meets.
5. Every finding of 50 or more, or a repeated class, leaves a committed check.
6. The orchestrator merges `main` in, posts `design-gate` from an independent verdict, runs and accepts `real-drawings` under the accept rule, runs `python -m scripts.merge_ready <PR>`, and merges.

Also kept:
- **Adversary rounds after each merge wave:** Sonnet 5.5 agents, one surface each. Any finding of 50 or more is re-run by an Opus `refuter` before anyone acts on it. M1's surfaces, in order:
  - the scorer and the key fence (element-level leaks);
  - the confirm service and the `attrs` walls;
  - the money chain (rounding, currency, allowance replacement);
  - the recognisers on hostile DWG;
  - the Held-out instance's separation;
  - the 3D viewer's inputs.
- **Time:** elapsed against budget in every message to a builder. Suite output is kept under `.private/work/` (pytest `-rf`).

## The scored loop in M1
- **When:** once M1-01 has merged, the custody re-run is done, and the M1-02 and M1-05 keys are in custody.
- **Who:** every `local` reading ticket (M1-29, M1-30 to M1-41, M1-42's fixes) loops on the element level.
- **How:**
  1. After the builder's first READY, the orchestrator runs the posting run with `--score` on its head.
  2. It fans out agents, one local session each, **each on a different failing (family, storey) or sheet**, running `--no-post` one at a time under the lock.
  3. Their fixes land on the ticket's branch one at a time, and each is re-scored.
- **What is looped:** both reads (C1) are scored. The ticket's own family's n / N, on either read, is what the loop drives. Every other family's n / N is a guard: no family may lose a passing (family, storey) without a reason the reviewer judges.
- **Stop:** two scored heads in a row gain nothing, or the ticket's loop allowance runs out: ≤ 90 minutes inside its budget (ADR 0030's stop rule).
- **Record:** every scored head goes in the M1 milestone issue, counts only.

Values are decimal strings in SI mm. Positions are in the **grid frame**: the origin is the key's named grid intersection, the axes run along the two grid directions, and the offsets are measured along them.

**The element join** (ADR 0015's identity, expressed in numbers):
1. The scorer converts the export's positions into the same grid frame, using the export's own grid lines with the same labels (C1's `grid`). If the export has no line with an origin label, every element of the set fails with the reason "grid frame not found".
2. Candidates must match on family and storey key.
3. Joins are one to one, nearest first, within these radii:
   - pile and pile cap: 300 mm (the cap by its centroid);
   - column: 150 mm between centres;
   - shear wall and lift core: axis overlap ≥ 50 % of the key's length, with axis offset ≤ 150 mm;
   - beam: both segment ends ≤ 300 mm;
   - slab: polygon IoU ≥ 0.8;
   - slab edge: overlap of the host edge ≥ 50 %, offset ≤ 300 mm;
   - storey: slab level ≤ 25 mm;
   - grid line: equal label after normalising case and whitespace, else parallel within 1° and ≤ 50 mm.
4. A mark is never used to join.

**Attribute tolerances:**
- section sizes, pile diameter and slab thickness: ≤ 1 mm (the exact inch conversion, ADR 0008);
- levels: ≤ 5 mm;
- lengths: ≤ max(1 %, 25 mm).

**What n / N means:**
- *Element rows:* N = the key's element count per family per storey. n = elements joined with every scored attribute within tolerance. Also reported: joined by position only, and phantoms (export elements that join nothing), counted apart. There are no exclusions in an unattended read. Excluded elements keep their place in N in the product (M1.md:308), and the project export (C13) counts them apart.
- *Counts only:* n = Σ min(export count, key count) and phantoms = Σ max(0, export − key), per (family, storey).
- "Changed attributes per family" (ADR 0030) counts the scored attributes above that differ, run to run.

**Planted contradictions:** a hit is an export Question whose family and storey match and whose message code is in the kind's code list (C10's `COUNTS_AS`). The scorer reports "raised k of K".

**The zone lines** (Edison, Held-out): `{"zones": [{"zone": "typical", "storeys": ["floor_3"], "lines": [{"item_code": "<a BOQ Item of the signed Rule Set>", "billing_unit": "cft", "quantity": "1234.56"}]}]}`. The scorer maps export storeys to zones from the key (M1.md:1125). It compares each line with the finish-line table's tolerance (M1.md:1437-1465). A zone's ৳ is the key's quantities priced at the export's rates, ±2 %.

**Who drafts** (the 24s route, M0.md:709-721):
- **Edison counts** (M1-05): `drawing-analyst` agents that read the PDFs, their text layer, their vector circles and renders, and never the pipeline's export or code. Two agents count each family independently; every disagreement goes to the owner.
- **The Sample Project's rows** (M1-02): reduced from the generating inputs by a script run as the key user (handed over outside the repo). Fallback, if the inputs lack them: the same analyst route as Edison.
- **Held-out counts and every Hand Takeoff:** the team engineer on the key user's side. Never a build agent.
- The drafts sit in `.private/work/keys-draft/m1/`, which no builder is pointed at.

**The owner's step:**
- confirms the drafts from a review page (each render beside its drafted counts; about 1.5 h per set);
- runs `scripts/owner/keys-custody.sh` (extended by M1-01 to move the M1 files), which moves the files, never copies them;
- no scored loop starts until custody.

**Owner only (one fact):** do the Sample Project's generating inputs hold each element's position and sizes and the list of planted contradictions, in a form the key user can reduce? Only the owner knows what the generating agent kept (ADR 0004 History). This is asked first in session 08. It blocks only M1-02's route choice, never the plan.
