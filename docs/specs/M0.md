# M0 "Drawings in": specification

Draft of 26 Sep 2026, for the owner's sign-off. It follows the to-spec template, then adds the finish
line, a sketch of the tickets and the open questions. Terms are `CONTEXT.md`'s. Where this page and an
ADR disagree, the ADR wins until the owner rules; the three places this spec asks to change an ADR
are listed under "Open questions". The plan (`docs/plans/M0.md`) comes next and may re-cut the
tickets, but not the scope.

## What is broken, unmeasured or missing before M0 can start (read first)

- **The Answer Key custody is set up (26 Sep 2026)**, with the scorer still a placeholder: vx-score is
  built in ticket 05 (ADR 0026).
- **The merge gate does not exist yet.** The rulesets API returns HTTP 403 ("Upgrade to GitHub Pro")
  today, so ADR 0025's enforced owner-only merge and the required `real-drawings` status cannot be
  set until the owner buys GitHub Pro.
- **The cloud environment has never run.** `scripts/cloud/setup.sh` says "NOT YET RUN IN A CLOUD VM".
  Unknowns that bear on M0: whether `gh release download` from our private repo works there, whether
  uv reaches its Python host, whether bwrap can create a sandbox inside the VM, and whether Chrome
  runs there for a browser test (docs/research/sdlc-waves-and-cloud.md §8).
- **No expected N exists for any M0 measure.** ADR 0030 says the owner writes them in M0; nobody has
  yet. They are Answer Keys, so this spec states none of them.
- **Nothing in M0 proves Vextrus reads an unseen consultant's drawings.** M0 runs on the two
  Development Sets only; the first Held-out Set is M1's (ADR 0005). M0 proves the foundation and that
  nothing regresses, not reading in general.
- **Unmeasured things M0 relies on:** the sheet renderer on a real GPU (every 2D frame time so far is
  SwiftShader, docs/research/viewer-2d-fidelity.md), a single-stroke font for SHX text (proposed,
  not measured), peak RAM of a whole read of the Edison set, the Bangla-ANSI font case on any real
  file (unverified whether either set has one), and how a QS reacts to any screen.

## Problem Statement

A Developer's QS has a Drawing Set as a handful of AutoCAD files and, sometimes, the PDFs plotted
from them. Each file holds dozens of sheets laid side by side in model space, sometimes in paper-space
layouts too, each sheet with several views (plans, sections, schedules, details, notes). Before
anyone can measure anything, someone must know which sheets there are, what each one is, which
storeys it shows, and that nothing on any sheet has been silently skipped. Today the QS does that by
eye, in AutoCAD, every project.

For Vextrus the same step is the first failure point: the prototype's sheet segmentation read 0 of
38 and 0 of 29 sheets on the Sample Project until it was fitted by hand, and a sheet region drawn too
wide produced dozens of phantom columns on the Edison set
(docs/research/sample-project-first-read.md; docs/research/2d-to-bim-prototype-lessons.md). An older
DWG decoder lost a whole file while every count check passed (docs/research/dwg-reader-evidence.md).
A sheet viewer that drops title-block attributes and leaders would show the QS something other than
what was read (docs/research/viewer-2d-fidelity.md). And nothing in the product exists yet: no
repository skeleton, no tenancy, no sign-in, no upload, no job, no CI.

The owner needs a foundation that every later milestone builds on without rework, proven on the real
Development Sets, and walkable in the running product.

## Solution

The QS signs in, opens a project and drops in the Drawing Set's DWGs, with their PDFs where the
Developer has them. Vextrus stores each file, reads it with LibreDWG 0.14 in a sandbox, checks the
read against a second, independent decoder (ACadSharp), and quarantines any file on which the two
disagree. It tells the QS which fonts it substituted, whether any Bangla text is set in a legacy ANSI
font, and, for each PDF, what the PDF can and cannot carry.

Vextrus then splits every file into sheets. It proposes each sheet's number, title, Discipline and
storey range, and finds the views on each sheet with their kind and title, marking not-to-scale
views. It draws every sheet with its own renderer, from the same entities it read: white paper and
black linework by default, a CAD-dark canvas one switch away, and the consultant's own plotted PDF
page registered beneath it (the Plot) where one exists.

The QS works this list as Takeoff Step 1, "Sheets": it confirms the agreeing sheets in bulk, fixes
or answers the exceptions, and excludes what is out of scope with a reason. Coverage shows every
view on every sheet as either assigned to the Takeoff Step that will read it or excluded with a
reason, with none unaccounted.

Behind this sit the modular monolith and its layers, tenancy with row-level security, the three
roles, the jobs, CI, the blind scorer and the real-drawing check. These are built once, in M0, so
M1's tickets add families, not plumbing.

### What belongs in M0, and what moves to M1 or later

M0 keeps what its finish line needs, plus what is far cheaper now than later: everything that touches
every table or every module (tenancy, the Trace anchor type, the event outbox, CI's migration rules),
and the proof mechanism itself (the scorer and the real-drawing check). Everything else waits for its
first consumer.

## User Stories

### The QS: getting in and starting a project
1. As a QS, I want to sign in with my email and password, so that I reach my Developer's projects and no one else's.
2. As a QS, I want to see my Developer's projects in a list, so that I can open the one I am working on.
3. As a QS, I want to create a project with a name, a code and an address, so that its Drawing Set has a home.
4. As a QS, I want the project to default to imperial Display Units, so that it matches how Dhaka measures without my setting it.
5. As a QS, I want every screen I use to be desktop-sized and to say so plainly on a phone, so that I am not given a broken layout.

### The QS: uploading
6. As a QS, I want to drag the Drawing Set's DWG files into the project, so that I can start without converting anything.
7. As a QS, I want to add the PDFs plotted from those DWGs beside them, so that Vextrus can show me the consultant's own plot.
8. As a QS, I want to see each file's upload progress and then its reading progress in words ("Reading sheet 12 of 38"), so that I know it is working and roughly how long it will take.
9. As a QS, I want to cancel a file's reading, so that a wrong upload does not hold up the rest.
10. As a QS, I want uploading the same file twice to do nothing the second time, so that I cannot create duplicate sheets.
11. As a QS, I want a file that failed or stalled to be retried without my asking, so that a server restart does not strand my upload.
12. As a QS, I want to add a file after I have started (the architectural set arriving after the structural), so that the list grows without starting again.
13. As a QS, I want a scanned PDF to be refused with the reason, so that I ask the Developer for the DWG instead of waiting for a result that will not come (ADR 0014).

### The QS: what Vextrus tells me about the files
14. As a QS, I want to know that each DWG was read by two independent decoders that agreed, so that I can trust the sheet list is the whole file.
15. As a QS, I want a file on which the two decoders disagree to be quarantined with a Question ("this file may be misread"), so that nothing built on a misread file reaches my figures (ADR 0029).
16. As a QS, I want the quarantine Question to tell me what to do (re-save the file from AutoCAD, or send it to Vextrus), so that I am not stuck.
17. As a QS, I want a font report per upload that lists every font the drawing names and the font Vextrus drew it with, so that I know why text may look slightly different from AutoCAD.
18. As a QS, I want to be told when Bangla text is set in a legacy ANSI font (Bijoy, SutonnyMJ), so that I know that text will read as Latin letters and will not be understood.
19. As a QS, I want a PDF's report to say who produced it, whether its SHX text survives as comments on each page, whether pages are rotated, whether its layers are present, and whether it has images, so that I know what the PDF can and cannot give.
20. As a QS, I want the PDF report, when a page's text is drawn as strokes, to name the exact AutoCAD setting for a re-plot, so that I can ask the consultant for the right thing.

### The QS: the sheet list (Takeoff Step 1, "Sheets")
21. As a QS, I want every sheet in every file listed with its proposed number, title, Discipline and storey range, so that I see the whole Drawing Set at once.
22. As a QS, I want the sheets grouped by Discipline and ordered by sheet number, so that the list reads like the consultant's drawing register.
23. As a QS, I want each proposal to show where it was read from (a title-block attribute, or text in the title block), so that I can judge it.
24. As a QS, I want a storey range read from the title in the drawing's own words and normalised ("2nd–8th floor"), so that I can check it against the title at a glance.
25. As a QS, I want a sheet whose title states no storey to say "not stated", never a guess, so that I know to look.
26. As a QS, I want to confirm every agreeing sheet in one act ("Confirm 36 sheets ↵"), so that the list takes minutes, not an hour.
27. As a QS, I want the exceptions pulled out first (a missing number, a duplicate number, a storey not stated, a low-confidence proposal), so that my attention goes where it is needed.
28. As a QS, I want to correct a sheet's number, title, Discipline or storey range in place, so that a reading error is fixed once.
29. As a QS, I want to exclude a sheet with a reason (an MEP sheet, a superseded sheet, a cover), so that it is kept but not read.
30. As a QS, I want an excluded sheet to stay in the count with its reason, so that the total still matches the drawings.
31. As a QS, I want sheet counts shown as n / N with N taken from the drawing where the drawing states it (its drawing register, the PDF's pages), so that I can see a missing sheet.
32. As a QS, I want to answer a Question by picking from the options Vextrus found, so that I never face an empty text box first.
33. As a QS, I want answering a Question to confirm the sheets it held, so that I am not asked twice.
34. As a QS, I want to undo my last Confirmation, so that a slip costs nothing.
35. As a QS, I want to do all of this from the keyboard (Enter confirms, arrows move, X excludes, E edits, number keys answer), so that I work as fast as in the Takeoff's other steps.
36. As a QS, I want Step 1 to show as confirmed on the step rail once every sheet is confirmed or excluded, so that I know I can go on (in M1).

### The QS: views and Coverage
37. As a QS, I want every view on a sheet outlined, with its title and its kind (plan, section, schedule, detail, notes, title block, legend), so that I can see the sheet's parts.
38. As a QS, I want a detail drawn inside a plan sheet to be its own view, so that its members are never mistaken for the plan's.
39. As a QS, I want a view marked not to scale to say so, so that I know only its text will be read.
40. As a QS, I want the scale a view states ("1:100") shown with it, so that I can see it before it is confirmed in the grid step.
41. As a QS, I want Coverage to show every view either assigned to the Takeoff Step that will read it or excluded with a reason, so that nothing is silently unread.
42. As a QS, I want to exclude a view with a reason, or re-assign it to another Takeoff Step, so that Coverage matches what I know of the drawings.
43. As a QS, I want the Coverage count on the status bar ("412 views: 390 assigned, 22 excluded, 0 unaccounted"), so that I see at a glance that nothing is missing.

### The QS: the sheet viewer
44. As a QS, I want a sheet to open as the consultant plotted it (white paper, black lines, true lineweights), so that it looks like the print on my desk (ADR 0032).
45. As a QS, I want one switch (D) to a CAD-dark canvas with AutoCAD's layer colours, so that I can think in model space when I need to.
46. As a QS, I want a Plot switch that shows the consultant's own PDF page registered beneath the drawing, so that I can compare what Vextrus read with what was plotted.
47. As a QS, I want the Plot switch to say "no Plot for this sheet" and why (no PDF, or its page could not be matched), so that a missing underlay is never a mystery.
48. As a QS, I want title-block attributes, leaders, multileaders, hatches, linetypes and lineweights drawn, so that nothing on the sheet is missing that AutoCAD shows.
49. As a QS, I want drawing text decoded before I see it (Ø, °, ± rather than %%C, %%D, %%P; line breaks rather than ^J), so that I never read raw CAD codes.
50. As a QS, I want a sheet to open fitted to its working area and never as a speck, so that I can read it at once.
51. As a QS, I want pan and zoom to feel instant on the densest sheet, so that working a sheet is not a chore.
52. As a QS, I want text too small to read at the current zoom drawn as grey bars, so that the sheet stays calm while I pan.
53. As a QS, I want the cursor's position in feet and inches on the status bar, never grouped in lakh, so that coordinates read as a drawing's do.
54. As a QS, I want to page through the sheets with the arrow keys, so that I can check a whole Discipline quickly.
55. As a QS, I want a sheet I have opened before to open again within a second and a half, so that going back and forth costs nothing.

### The MD
56. As an MD, I want to sign in and see my Developer's projects and their sheet lists, so that I know where each project stands.
57. As an MD, I want to be unable to confirm or edit the Takeoff, so that the QS's work is the QS's.
58. As an MD, I want to invite a Vextrus Engineer to my Developer's data for a set time, so that Vextrus can sit with my QS through the first Takeoff.
59. As an MD, I want to see who from Vextrus has access, and until when, and to revoke it at any moment, so that I stay in control of my data.
60. As an MD, I want every action a Vextrus Engineer takes recorded under their own name, so that I know who did what.
61. As an MD, I want to invite a QS from my firm, so that my team can work without Vextrus.

### The Vextrus Engineer
62. As a Vextrus Engineer, I want to enter a Developer's data only through that Developer's invitation, so that the client trusts us with it.
63. As a Vextrus Engineer, I want to work as a QS inside the invitation (upload, confirm, answer), so that I can help the client's QS through Step 1.
64. As a Vextrus Engineer, I want my access to end by itself when the invitation expires (30 days by default, renewable), so that no stale access lingers.
65. As a Vextrus Engineer, I want to see nothing of any Developer that has not invited me, even through the admin, so that a mistake cannot leak one client's data to another.

## Implementation Decisions

### The shape and the modules
- **One Django 6.1 + Ninja application, Python 3.13 via uv, Postgres 16, one React 19 + Vite app**
  (ADRs 0034, 0022). All 13 modules (`platform`, `projects`, `drawings`, `building_model`,
  `takeoff`, `measurement`, `rates`, `boq`, `revisions`, `summary`, `exports`, `assistant`, and the
  pure `engine`) are created as stubs in the first ticket, with their anatomy (models, migrations,
  services, schemas, http, admin, tasks, tests) and the import-linter contracts (layers, sibling
  independence, private models, `engine` importing no Django and no module). The shared files
  (installed apps, the root router, the import-linter config, CI) are written once, there.
- **M0 fills four modules and `engine`:** `platform`, `projects`, `drawings`, `takeoff` (Step 1
  only). The rest stay empty stubs.
- **Each worktree gets its own database, named by an environment variable; test databases are named
  by a hash of the migrations** (docs/architecture.md). The OpenAPI schema and the generated
  TypeScript types are built in CI and never committed.

### `platform` (layer 0)
- **Tenancy.** The Developer is the tenant. Every tenant table has `tenant_id` and a forced policy in
  its first migration, `tenant_id = current_setting('app.tenant_id')`, set per transaction from the
  request's Membership; the app connects as a non-owner role. Library-readable tables (the Takeoff
  Steps and the Check catalogue in M0) use the "L" variant: the Library tenant's rows are readable by
  every tenant and writable by none (docs/data-model.md §2). A CI test enumerates every table and
  fails when one lacks a forced policy.
- **Users and Memberships.** A user may hold Memberships in several Developers. Roles: `qs`, `md`,
  `vextrus_engineer`. A Vextrus Engineer's Membership is created only by an invitation from that
  Developer's QS or MD; it has a required expiry (30 days by default, renewable), can be revoked, and
  is listed to the client with its dates. Every act is recorded under the acting user.
- **Auth.** Email and password, server sessions and CSRF protection from Django. MFA and rate limits
  are M5. Developers are created by Vextrus staff through the admin; there is no self sign-up in M0.
  Invitations are links the inviter copies; email delivery waits for the beta.
- **The admin obeys the same policies:** it runs under a tenant context like any request.
- **Storage.** Put and get by key on the local file system in development (S3 at the beta), each file
  recorded as a StoredFile with its sha256, kind (original, derived), producer and producer version,
  and source sha256.
- **Jobs.** A thin wrapper over Procrastinate: defer in the same transaction as the data, arguments
  of tenant id and ids only, the tenant set before any data is touched; a `cad` queue at
  concurrency 1; progress and cancel per job; a periodic retrier for stalled jobs; steps keyed so a
  re-run skips completed steps.
- **Events.** Each domain act writes one DomainEvent row (ids and counts only) in its own
  transaction.
- **Jev client.** `ask(node, facts, question, options) → answer with confidence | unavailable`; a
  per-tenant answer cache keyed by (facts, question, options, model version); an override log when the
  QS changes a Jev proposal; recorded answers by default in tests, live calls only in tests marked
  live, and never with the owner's key in cloud sessions (ADR 0013).

### `projects` (layer 1)
- A Project has a code, name, address, market (`BD`) and Display Units (imperial by default).
  Services: create, get, list. One Drawing Set per project in the MVP (docs/data-model.md §7).

### `drawings` (layer 2)
- **Tables as in docs/data-model.md §3.2:** Drawing Set, Revision (M0 writes only the first issue),
  Drawing File, Sheet, Sheet Revision, Drawing Set State (seq 1, cause first read), State Sheet, View.
  M0 adds these fields, which the data model lacks:
  - on Drawing File: the read step and sheets done / total (progress); the font report; the
    Bangla-ANSI finding; for a PDF, its upload report;
  - on Sheet: the storey range as stated (verbatim) and normalised (first and last storey in a
    canonical vocabulary: pile, pile cap, foundation, basement n, ground, 1st…nth, roof, stair-room
    roof, or "not stated"). M1's Takeoff Step 3 binds each confirmed range to storey Elements;
  - on State Sheet: the per-sheet render artefact, and the Plot (PDF file, page, registration
    transform and residual), or the reason there is none;
  - on View: the not-to-scale flag and the stated scale text (the confirmed scale stays empty until
    M1).
- **Services (public):** add a file to a project's Drawing Set (idempotent by sha256; the PDF beside
  its DWG); run one read step for a file; record sheets and views from the engine's results; apply
  Step 1's confirmed facts to sheets and views (called only by `takeoff`'s confirm service);
  `resolve(anchor)`; fetch a sheet's render artefact and its Plot.
- **The Trace anchor** is a value type owned here: (source sha256, reader and version, sheet, the
  chain of insert handles, entity handle) for a DWG; (page, path index, box) for a PDF. An artefact
  any anchor names is never deleted. `drawings` raises no Questions; it reports quarantine and
  findings, and `takeoff` raises them.

### `takeoff` (layer 4): Step 1 only
- **Tables as in docs/data-model.md §3.4, the Step 1 subset:** Takeoff Step (library rows, all 14,
  only Step 1 live), Step Progress, Recognise Run, Proposal (subjects `sheet` and `view`), Proposal
  Trace, Confirmation, Question, Question Link, Check, Check Run, Check Finding, Coverage.
- **The read-and-propose job lives here,** not in `drawings`: it orchestrates the per-file then
  per-sheet read steps through `drawings.services` (downward), calls the engine's recognisers, sends
  the engine's judgement requests to Jev (or leaves them to the QS), and writes Proposals, Questions
  and Coverage. This keeps every call downward; `drawings` never needs to know about `takeoff`.
- **The confirm service** is the only path that writes confirmed sheet and view facts, through
  `drawings.services`. Bulk and single Confirmations, answers that confirm what they held, exclusions
  with a reason, and undo are all Confirmation rows (append-only).
- **Coverage in M0:** every View gets a Coverage row. A view is accounted for when it is assigned
  to the Takeoff Step that will read it (proposed from its kind and title, confirmed with the sheet
  list) or excluded with a reason. "Used" is set only when a later step's Confirmation draws on it.
  This needs a status the data model lacks, `assigned` (open question 1).
- **The Checks catalogue's first entries** (each a pure function in `engine`, versioned, naming M0):
  - **Two decoders agree** (handle set, per-type and per-layer counts): a disagreement quarantines
    the file and raises a `file_misread` Question.
  - **Bangla text in a legacy ANSI font:** by the style's and inline fonts' names and by the text's
    byte pattern; it raises a flag with the fonts named (ADR 0031 §11).
  - **The drawing register:** where the set carries a list of drawings, its entries against the
    sheets found, both ways.
  - **The Plot's pages:** where a PDF exists, its pages against the sheets found, both ways (a sheet
    plotted twice, a sheet not plotted).
  - **Storey in the title against storeys in the view titles** on the same sheet.
  - **Coverage:** no view unaccounted.

  A duplicate sheet number, a missing number or title, and a storey Jev answered with low confidence
  are Questions of kind `conflict`, `missing` or `low_confidence`, not Checks: nothing independent is
  compared.
- **Step Progress** shows sheets n / N (N from the register or the Plot where one exists, otherwise
  "—") and the open Questions, and records active time (telemetry for the owner, never shown to the
  client, ADR 0033).

### `engine` (pure Python, no Django)
- **`read`, behind one reader interface:** `read(file) → ReadArtefact` with the reader's name and
  version. The artefact holds every entity with its handle and insert chain, layouts, blocks,
  layers, text runs with their style and font, and the header units.
  - LibreDWG ≥ 0.14 (pinned by `toolchain/libredwg.version`) as sandboxed subprocesses: geometry by
    `dwg2dxf` → ezdxf, text from `dwgread` JSON (never from the DXF, which corrupts raw line
    breaks), each ATTRIB's style inherited from the ATTDEF with the same tag (LibreDWG drops it).
  - ACadSharp (MIT, .NET) through a small dumper of our own, sandboxed, producing the same summary
    (handle set, counts per type and per layer); a comparator returns agree or the differences.
  - The sandbox: bwrap with no network, the file system read-only except one output directory,
    CPU-time and memory limits, and a wall-clock timeout; the same runner for every subprocess
    reader.
  - PDFs: pdfplumber / pdfminer.six and pypdfium2 only (never PyMuPDF), for the upload report
    (producer, SHX comments per page, fonts, `/Rotate`, layer names from each page's resources,
    images and their area, scan refusal) and for the page text used to match pages to sheets.
- **`recognise`, returning candidates plus judgement requests:**
  - sheets: from repeated title-block frames in model space and from paper-space layouts; number,
    title and revision mark from title-block attributes where they exist, from text inside the
    title block where the block was burst or has no attributes; Discipline from the number's prefix
    where it has one; each candidate carries its anchors;
  - views: boxes, titles, kinds, the not-to-scale flag and the stated scale text; a detail inside a
    plan is its own view; each view's proposed Takeoff Step or exclusion reason;
  - judgement requests for Jev: the sheet's type and first and last storey, given code-computed
    facts (the title, the Discipline, the view titles) and the canonical storey options. Code
    expands the range and checks first ≤ last.
- **`render`:** one sheet at a time, never a whole file: thin lines as GL_LINES, lines of visible
  plotted width as quads, text as SDF glyphs, hatches, linetypes and DWG lineweights, every primitive
  carrying [top-level handle, nested handle, type, layer], in a sheet-local origin. Text is decoded
  (`%%C`, `%%D`, `%%P`, `^J`, stacked fractions) and set with the font substitution table, which uses
  redistributable fonts only (Liberation Sans, Serif and Sans Narrow; DejaVu; a single-stroke font
  for SHX) and records every substitution for the font report. Overlapping glyph contours fill by the
  nonzero rule.
- **Page-to-sheet registration:** match each PDF page to a sheet by its title-block text and sheet
  number, then fit scale, rotation (in 90° steps) and offset; report the residual.
- **Scoring helpers for the render check:** raster the sheet's buffers and its registered Plot at a
  fixed size and return recall, precision and F1 within 2 px (the method of
  docs/research/viewer-2d-fidelity.md).
- **An export** of what was read and proposed per Drawing Set (sheets, numbers, titles, Disciplines,
  storey ranges, views and kinds, Coverage, locations), which is what the scorer compares.

### The web app
- **App shell** on the accepted design system: its tokens, Archivo and the "Vextrus Taka" fallback,
  Lucide icons, shadcn primitives styled by the tokens; the 40 px top bar, the step rail (the 14
  Takeoff Steps, only Step 1 live), the canvas toolbar, the docked inspector (Selection | Questions)
  and the status bar (cursor in ft-in, stated scale, Coverage). Sign-in, the project list and
  creation, members and invitations, the Drawing Set (upload, files, their reports and progress), and
  Step 1 (the sheet list, the viewer, Questions, Coverage).
- **Formatting** by kind: length and coordinate in ft-in (never grouped), counts as n / N, dates as
  "26 Sep 2026". Money and quantities wait for M1.
- **The sheet viewer** is plain WebGL over the engine's buffers: Paper by default, CAD-dark on D, the
  Plot underlay through pdf.js with the registration transform, fit to the sheet's working area,
  text below 6 px drawn as grey bars, view outlines with their kind and state, a scale bar showing
  the stated scale. Buffers are cached in the browser per sheet.
- **Types** are generated from the OpenAPI schema at build time.
- **The design gate** applies to every UI PR: `ux-critic` walks it at 1440×900 and 1280×800 with
  screenshots (docs/sdlc.md).

### Harness pieces M0 adds (each an owner-approved change, docs/sdlc.md)
- **vx-score**, the blind scorer: compares a Vextrus export with an Answer Key and prints only
  aggregates per measure (n / N, phantoms, and the change from the last merged run). It never prints
  a key value, a name or a title. A sheet matches a key sheet when their frames overlap by IoU ≥ 0.9
  (or share a layout); a view when IoU ≥ 0.8 and the kind agrees; a title when it is equal after
  normalising case, whitespace and decoded symbols; a storey range when first and last are equal (or
  both "not stated"). The plan may tune the thresholds, never after seeing a result.
- **The owner's `real-drawings` command:** runs as `vxkeys`; checks out the PR's head into the key
  user's scratch space; runs the product's read-and-propose job over every Development Set against a
  throwaway database (the engine-only harness until that job exists); exports; scores; posts the
  `real-drawings` status with aggregates only. A CI job posts "not applicable" when the diff touches
  no engine or reading path.
- **The `real-drawings` skill** is updated to say where expectations now live (with `vxkeys`, not
  `.private/work/checks/`).

## Testing Decisions

- **A good test checks behaviour through the highest seam that can see it,** never an
  implementation detail. Synthetic fixtures prove mechanics only; they are never offered as proof of
  reading (docs/sdlc.md).
- **The seams, highest first:**
  1. **The owner's walk** on the reference setup, on both Development Sets. The only "done".
  2. **The real-drawing check** (`local`): the product's pipeline on both Development Sets, scored
     blind against the M0 keys (sheets, numbers, titles, Disciplines, sheet → storey, views,
     Coverage, render-check F1 per sheet, Plot pages matched, decoder agreement, and peak RAM and
     time per file). Required on every PR that touches `engine` or the reading modules.
  3. **The HTTP API with a real Postgres, RLS on and the app's non-owner role,** with jobs run in
     the test (`cloud`). One test drives the whole Step 1 on a synthetic DWG: upload, read job,
     proposals, a Question, bulk Confirmation, Coverage with none unaccounted, idempotent
     re-upload, cancel, a stalled job retried.
  4. **The engine's public functions** (`cloud` on synthetic fixtures): read, cross-check,
     segment, views, render, PDF report, registration, the Checks.
  5. **One browser smoke test** (`cloud` if Chrome runs in the VM; unverified): sign in, upload,
     see the sheet list, open a sheet, confirm.
- **What `cloud` tests prove:** tenancy isolation (a second Developer's user sees nothing through
  the API or the admin); the policy-coverage test; the import layers; migrations (none missing, one
  leaf per module); the sandbox (the reader cannot open a socket or write outside its output
  directory, and is killed at its memory and time limits); the job semantics (idempotent steps,
  progress, cancel, the retrier); the cross-check's logic (a stubbed second decoder that disagrees
  quarantines the file and raises the Question); the reader mechanics on committed synthetic DWGs
  (title blocks with and without attributes, a burst title block, a detail inside a plan, a
  paper-space layout, raw line breaks in MTEXT, an ATTRIB with a null style); the PDF report on
  synthetic PDFs (rotation, SHX-comment annotations, an image-only page refused); the Jev client's
  cache, override log and fallback with recorded answers; the scorer on invented keys (and that it
  prints no key value); the formatters against a table of expected strings.
- **What `cloud` tests cannot prove:** that any of it reads a real consultant's drawings, that a
  sheet is legible, or any frame time. Those are `local`.
- **Fixtures.** Small synthetic DWGs are generated by a committed script with a writer whose licence
  permits it (ACadSharp's writer or LibreDWG's; the plan picks after checking the licence, ADR 0031
  amendment). Nothing derived from a real set is ever committed.
- **The frontend** is tested at the component level where behaviour lives (the sheet list's
  keyboard, the Question card, the formatters); the viewer's fidelity is the render check's job, not
  a unit test's.
- **Prior art:** none in this repository yet; the method of the render check and the decoder
  comparison come from docs/research/viewer-2d-fidelity.md and dwg-reader-evidence.md.

## Further Notes

- **Why this is still a big milestone.** Most of M0's size is plumbing that every later milestone
  would otherwise build under pressure: tenancy in every table, a job system that survives restarts,
  a decoder cross-check, a sandbox, the proof mechanism. What was cut went to its first consumer
  (scale → the grid, picking → the Trace, hand correction → the Held-out Set, 3D → M1).
- **The first local ticket is the skeleton,** not a cloud one. It writes the shared files and `.github/`
  the owner reads in full, and the cloud environment's checklist needs `uv sync` and an empty test
  suite to pass on it (docs/research/sdlc-waves-and-cloud.md §6.5).
- **The design tokens live in `.private/work/session-01/design/`,** which cloud sessions cannot
  see; ticket 01 (local) copies them into the web app. They hold no drawing content.
- **Risks the plan must answer:**
  - bwrap may not run in the cloud VM or on the CI runner if unprivileged user namespaces are
    restricted there (it works on this machine: bubblewrap 0.9.0). If not, the sandbox tests run
    locally and in CI only, and the plan says so.
  - The Edison PDFs were merged by a PDF tool and their DWG revision is unknown; 52 of 57 structural
    pages registered in session 01 (docs/research/vector-pdf-evidence.md). Some Plot pages may not
    match; each such sheet says why.
  - The single-stroke SHX font is proposed, not measured; SHX carries most of the Sample Project's
    structural text, so it bears on legibility.
  - Ubuntu's AppArmor, the .NET runtime size and the LibreDWG asset download all touch the CI and
    cloud images; ticket 01 and the owner's checklist find out.
- **Terms.** "Plot" (the consultant's PDF page registered beneath the sheet) and "view" are used as
  ADR 0022 and CONTEXT.md's Coverage use them; neither has its own CONTEXT.md entry yet. If the owner
  agrees, "Plot" gets one.
- **ADRs this spec would amend if the owner agrees:** ADR 0027 (Coverage's `assigned` status), ADR
  0030 (M1's keys at M1's start), ADR 0022 (the sheet's pan-and-zoom budget and the render-check
  threshold).

## Open questions for the owner (one at a time, recommendation first)

1. **What "Coverage accounts for every view" means in M0.** Recommendation: a view is accounted for
   when it is assigned to the Takeoff Step that will read it or excluded with a reason; "used" comes
   when that step's Confirmation draws on it (from M1). Why: in M0 no step after Step 1 exists, so
   without "assigned" every view would be "unaccounted" and the measure would say nothing.
2. **Bring Jev into M0 for one node, sheet type and storey range.** Recommendation: yes, with its
   answer cache, override log, QS fallback and a 30-sheet spot check. Why: code alone placed 11 of 16
   storey-bearing Sample Project sheets after fitting; Jev placed 48 of 48 invented titles and
   flagged the unclear one itself (docs/research/sample-project-first-read.md;
   docs/research/jev-system-one.md). The client is needed in M1 anyway.
3. **Write the M1 Takeoff Steps' expected N at M1's start, not in M0 (amends ADR 0030).**
   Recommendation: yes. Why: M0 cannot use them, they cost the owner hours, and M1's grilling may
   change what is counted.
4. **The render-check and sheet-smoothness targets.** Recommendation: every sheet F1 ≥ 0.90 against
   its Plot and the median ≥ 0.95, each sheet under 0.95 explained by a named loss; pan and zoom on
   the densest sheet at p95 ≤ 16.7 ms a frame on the reference setup, beside ADR 0022's 1.5 s for a cached
   sheet. Why: the prototype scored 0.834–0.972 on three sheets, with its worst losses in font
   substitution and inline formatting, which M0 fixes; ADR 0022 sets no frame budget for the sheet.
5. **Which laptop is "a mid-range Windows laptop".** Recommendation: a machine the owner or a team
   member already has, of about a Core i5 with Iris Xe and 16 GB, named now so every budget is
   measured on the same one. Why: session 01's GPU figures came from a desktop's integrated GPU
   through WSL, and every 2D frame time was software rendering.
6. **Who drafts the Edison M0 key, and from what.** Recommendation: a script run as `vxkeys` drafts
   it from the Edison PDFs (a route independent of LibreDWG), and the owner confirms it sheet by
   sheet; the Sample Project's key comes from its generating inputs (ADR 0005). Why: ADR 0030 needs
   an independent route and the owner's confirmation, and typing a whole set's titles by hand is
   slow and error-prone.
